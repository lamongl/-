# 成品工作台：Codex 本地版

用户调用 `deliver-workbench` 后，当前Codex通过本地MCP打开任务界面；用户拖入最多5份、每份20MB的材料并填写需求。当前Codex读取原件与提取文字，必要时在界面提出关键问题；收到回答后内部组织执行要求、使用宿主现有制作工具完成文件，并回传到下载区。中间提示词不展示、不作为成品保存，不另调模型API。

## 组成

Skill 1.1.0：复杂任务先读材料、分轮澄清（每轮1至3题），按用途、交付条件、内容取舍逐步形成制作方案；完整需求不重复询问。制作时区分证据和观点，按内容选择图示或表格，交付前检查硬性要求与实际文件。追问增加并不自动代表质量提升，效果需用同条件成品对照验证。

界面支持多轮追问，已确认回答可在各阶段展开查看。1.1.0验证包含四类行为场景（模糊需求、完整需求、容量冲突、简单修改）、Skill格式与安装同步检查、7项连接器/stdio回归，以及隔离浏览器两轮回答后历史保留和文件下载。安装包由 `python scripts/package-delivery-skill.py` 按白名单生成，不包含用户资料。

- `skills/deliver-workbench`：任务编排指令，默认直接交付成品。
- `bridge/server.mjs`：官方SDK实现的stdio MCP入口，提供7个任务工具。
- `bridge/core.mjs`：本机HTTP任务界面、原件与文字存储、追问和下载。
- `bridge/ui`：上传、确认思路、制作进度、成品下载的界面。
- `.workbench/jobs`：本地任务数据，不进入GitHub发布或安装包。

每次任务启动一个真实本机访问链接。外部GitHub Pages静态页面无法自行调用用户的Codex模型，因此第一版本地提供同一工作台，不依赖公共网页上传服务器。文件会保留在当前电脑，仍由所选AI宿主处理，不保证云端模型的数据不离开本机。

## 安装

1. 在项目目录执行 `npm ci`，需要Node.js 22.13+。
2. 将 `skills/deliver-workbench` 目录放入Codex用户技能目录。
3. 使用本机真实绝对路径配置：

```text
codex mcp add delivery_workbench -- <node绝对路径> <项目/bridge/server.mjs绝对路径>
```

刷新或重启MCP连接后检查7个工具：create_job、wait_for_submission、get_job、read_material、ask_questions、set_progress、publish_result。已有会话不保证自动加载新配置；新开会话或按客户端提示重启后再检查。

调用：`使用 $deliver-workbench 打开工作台，我要上传材料制作PPT。`

## 状态和边界

任务状态：等待资料→已提交→（可选）等待关键回答→制作中→已交付，失败时显示实际原因。上传完成不等于AI已经开始处理；`set_progress`由宿主真实开始制作时调用。仅当output目录有真实非空文件时才能交付；宿主还必须验证文件内容、可打开性及格式，连接器不能自动判断全部作品质量。

AI会话运行期间通过等待工具取得提交/回答。会话已结束或客户端长时间挂起后，不承诺浏览器提交会自动唤醒模型；回到原聊天说“继续完成工作台任务”即可由宿主继续。连接器进程关闭后旧的随机端口链接不能继续访问；磁盘资料仍保留，可由宿主依据任务记录恢复工作，但当前版本尚未提供自动恢复链接和已交付文件的新版本编辑接口。

其他AI宿主需要支持stdio MCP、本地文件访问及实际制作能力，并分别验收；只安装SKILL.md不能给普通聊天网页新增这些能力。没有目标格式制作工具时，应说明并与用户确认替代交付，不能用TXT改后缀替代PPT、Word或Excel。

## 验证记录

本地任务桥测试、真实stdio MCP协议测试，以及独立Edge浏览器的拖放→提交→关键追问→回答→回传→下载流程已通过；移动端无横向溢出，页面无未捕获异常。目录联接跨任务越界和页面恢复后停止轮询均已用回归场景复现并修复。测试中的合成报告不等于已证明所有PPT/文档制作质量，真实用户任务还需由当前Codex制作后验收。

原GitHub网页保持原样，待新流程的真实任务确认后再替换，避免把尚未接入宿主的页面发布成已经具备AI能力。

首次真实任务已完成：用户上传Word论文，在工作台回答关键问题后，当前Codex制作并回传8页英文答辩PPT，中文讲稿与答辩问答写入演讲者备注。最终文件通过结构、版面、字体与可导入性检查，并逐页渲染审阅。文件与任务内容属于用户资料，不包含在代码发布或安装包中。


## 通用发行包 1.2.0

自1.2.0起统一使用通用ZIP，不按平台分包。用户将整个包交给可读写文件、执行命令的Agent，要求读取 `INSTALL.md` 自动安装。Agent识别当前宿主，安装依赖并配置Skill与stdio MCP，再运行包内自检；需要宿主授权或刷新连接时如实说明。包内包含17个白名单文件，不含用户资料。

此版本保留1.1.0的质量流程和工作台界面，新增通用安装说明与 `scripts/verify-install.mjs`。用户确认Codex、腾讯WorkBuddy、豆包与DeepSeek的Agent环境均完成开发者实测，具体安装入口随工具版本而异。宣传页与本地上传、追问、成品下载工作台分开。

已将通用ZIP独立解压到临时目录，执行干净的 `npm ci --ignore-scripts --no-audit --no-fund` 安装110项依赖，再运行包内自检，确认7个MCP工具和本地任务接口可用。这不等同于在每个第三方Agent中自动配置均已验收。

## 1.3.0 窗口与界面

调用Skill后先创建任务，连接器自动请求Edge/Chrome独立应用窗口；失败时返回真实链接交由宿主打开。黑色背景、蓝色强调与宣传站一致，上传、追问、制作、下载共享同一任务。安装自检与自动回归关闭弹窗，旧安装需刷新连接加载新服务。启动请求成功不等于原生窗口可见性已验证。

## 所有宿主的工作台追问约定

提交材料后，宿主读取材料并调用 ask_questions，在原工作台展示问题。用户在界面提交至少一轮回答后，宿主才可请求开始制作和交付。需求完整时使用简短的方向确认。所有接入宿主共享连接器的状态检查，缺少 clarifications 的 processing 和 publish_result 请求会被拒绝。更新连接器后刷新MCP连接加载规则。已有已交付文件继续保留。

## 1.4.0 豆包安装适配

依据用户提供的豆包安装记录，明确 Markdown 完整还原、项目级镜像重试、依赖完整性验证和本地缓存恢复。优先接入并验收 MCP，服务端自检不代表宿主工具加载成功。新增用户选择后的 CLI 备用接入，与 MCP 共用 actions/core，跨命令复用隐藏后台，保留追问状态并通过服务发布。会话重启复用原端口和任务目录。源码还原、非法路径拒绝、错误依赖拒绝、跨进程任务、服务恢复与两种接入流程均有回归测试。豆包客户端的原生 stdio 注册入口仍待实际环境验收。
